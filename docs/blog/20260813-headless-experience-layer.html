What Headless Experience Layer is

For a long time, a Salesforce UI meant Lightning. If the same next action needed to show up in Slack, you rebuilt it in Block Kit. In ChatGPT or Claude, you hoped a paragraph would do. Three surfaces, three front ends, one tired team.

Headless Experience Layer is Salesforce’s answer to that split. Headless does not mean “no UI.” It means the UI is not locked to the Salesforce browser. You describe a card, a decision tile, a rebooking flow — once — as a small JSON tree. Slack, mobile, Microsoft Teams, ChatGPT, Claude, Gemini, Agentforce, or any MCP host renders it with their own look. You do not ship a second stylesheet. You do not paste markdown and hope.

Salesforce places HXL inside Headless 360: the wider bet that every platform capability should be reachable as an API, an MCP tool, or a CLI command, so humans and agents work on the same governed logic. HXL is the presentation piece of that bet. The agent decides what to do. The Experience Layer decides how that decision appears on whichever surface the user is already in.

Words the product uses. They are not interchangeable.
WordIn plain English
HXLHeadless Experience Layer. Describe the interface once. Let each host paint it.

MosaicThe JSON. Data (model) + tiles (view) + later, actions (controller).

MCPModel Context Protocol. The plug a host like Claude uses to call a tool and, here, mount a UI.

When Salesforce released it

Salesforce announced Headless 360 on 15 April 2026 at TrailblazerDX (TDX) 2026 in San Francisco. The Headless Experience Layer — also shown in the keynote as the Agentforce Experience Layer — shipped as a generally available UI service in that launch, not a slideware mock.

The public way to touch it is Explore the Playground on the product page. Every tutorial on that site is itself a widget. Expand the code view and you are reading the same JSON a host will render. That is the runtime, not a marketing picture of a runtime.

If you are coming to this in August 2026, HXL is a few months old. The docs and the playground are the source of truth. This post is how one sample used them — not an official Salesforce guide.

How it is meant to be used

Salesforce’s own examples are things a queue or a traveler would actually click: a flight status card, a rebooking flow, an approval, a case escalation, a renewal alert. The pattern is the same every time.

flowchart LR A[Business moment
case, renewal, approval] --> B[One Mosaic
semantic tiles] B --> C[Host paints it
Slack ChatGPT Claude Agentforce]
  1. Pick a moment that is more than text. If a paragraph is enough, you do not need HXL.
  2. Describe the interface in the playground with components and semantic variants. Bind data with expressions like {!$case.subject}. Use meta.if so a warning is absent when it is not true — not hidden with CSS.
  3. Let the host render. Slack looks like Slack. Claude looks like Claude. You do not restyle per channel.
  4. Keep trust on the platform. Headless is the presentation. Sharing, field-level security, and audit stay in Salesforce. Claude is another surface, not a copy of the org.

That is the intended loop. The rest of this post is how we learned that loop by building one card.

How we learned it: Case Next Action

We did not start with a platform essay. We started with a case a queue would recognize. Payment failed on a renewal. SLA has two and a half hours left. The agent — human or otherwise — needs the number, the customer, the burn, and the next move. The playground already had cousins of this (case summary, SLA status). We wanted the one you act on.

So we built Case Next Action: a mosaic with a card, priority and SLA badges, a warning callout that only exists when the case is at risk, a recommended next step, and one primary button. Sample data is fictional — Northwind Traders, case 00001234, owner Alex Rivera.

{
  "definition": "tile/callout",
  "meta": { "if": "{!$case.slaAtRisk}" },
  "attributes": { "variant": "warning", "title": "SLA at risk" }
}

When slaAtRisk is false, that block is not in the tree. Each host decides what “absent” means. That single line taught us more about HXL than the product headline did.

Then we did what the launch implied but did not finish for you: we wrapped the same idea as an MCP app so Claude Desktop could call get_case_next_action and mount the card in chat. The README is the recipe — mosaic, WidgetBundle, server, Settings → Developer → running. This is the path we actually walked.

The sample, running

After the server is running, a new Claude Desktop chat gets one line:

Show me the Case Next Action card

Allow the tool if Claude asks. You want the white card — not a paragraph that says “here is the card” with a spinner underneath. Click Take next action and the widget talks back into the thread. In this sample the buttons send a chat message. They do not update Salesforce. The lesson stops at “the host can render and click.”

First run we got a spinner. Claude wrote a confident summary. The iframe stayed blank. The HTML had not finished the MCP Apps handshake, and we had put an HTTP proxy in front of a server that wanted stdio. The README lists the fix. If a turn already broke, quit with ⌘Q and start a new chat. The host caches the widget aggressively.

What stays in Salesforce

Headless means the presentation can travel. It does not mean the case record should leave the platform. In a real org the same mosaic would bind through Salesforce — sharing, field-level security, audit — and Claude would be another surface.

If you want to repeat the sample, the story ends here. The clicks and file names are in the README.

Clone hxl-agentic-experience-layer, follow the README, ask for the card. That is how we learned HXL: one component, one host, no second UI kit.
